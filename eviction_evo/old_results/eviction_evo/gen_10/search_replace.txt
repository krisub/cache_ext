<DESCRIPTION>
The current program scores 1978.09, which is lower than a previous best of 2162.27. The regression appears to be from losing granular burst detection that could better distinguish between transient request spikes and sustained high-frequency load.

The recommendation suggests adding packet count velocity detection: instead of relying only on inter-arrival time (which the current code removed), track how many TCP packets arrive per unit time over a 100ms window. If the packet velocity exceeds a threshold (indicating sustained, not transient, load), apply aggressive 0.4x protection multiplier to recently-accessed folios, complementing the existing time-window-based thresholds.

This should:
- Better protect the working set during sustained high-frequency phases (dual_congested scenario)
- Distinguish between brief spikes (which shouldn't trigger aggressive caching) and sustained bursts (which should)
- Improve dual_small_vs_large where we have one fast reader maintaining steady request rate
- Potentially recover some of the lost performance vs the 2162.27 baseline

Implementation: Track net_recv_count snapshots at eviction time, compute packet velocity over 100ms windows, and apply conditional 0.4x multiplier to protect recently-used folios when velocity indicates sustained load.
