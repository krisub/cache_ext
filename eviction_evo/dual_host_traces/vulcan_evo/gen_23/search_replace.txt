<DESCRIPTION>
The current program implements recency-aware loss detection via RollingWindow (rw_size=5) for GF_LOST, but this can be further refined by explicitly tracking the timestamp of the last loss event and applying time-decay to the loss boost factor. This prevents stale loss signals from causing sustained over-protection of the cache after network conditions recover.

The key insight from the recommendation is that loss signals should naturally decay over time. We currently apply full 15% boost whenever max_lost > 0 via the multi-tier logic, but we should decay this boost exponentially based on how long ago the last loss occurred. This way:
- Recent loss (< 10ms ago): full 15% boost (boost_factor = 115)
- Moderately old loss (10-50ms): partial boost decaying toward baseline (105% down to 100%)
- Stale loss (> 50ms): no boost (clamped to 100%)

This prevents the conservative over-protection that lingers after transient network events, allowing the cache to resume normal eviction once the network stabilizes.

Changes:
1. Add a static `last_loss_ts` variable within EVOLVE-BLOCK to track the most recent loss detection timestamp
2. Update `last_loss_ts` in `bpf_score_fn` when loss is detected
3. Replace the multi-tier loss boost logic with a single exponential-decay formula
4. Revert the asymmetric penalty scaling logic (cold_penalty) that appears to have degraded performance compared to the simpler version
</DESCRIPTION>
