introduce_promotion_tier_for_very_hot_folios

<DESCRIPTION>
The current program protects very_hot folios (access_count ≥ 5 after decay) only during active sessions, which may under-protect pages that are genuinely critical across workload phases. The recommendation suggests implementing a separate promotion list for folios that reach access_count ≥ 7 (after decay), protecting them with a longer window (e.g., 200ms instead of 100ms) even during moderate congestion.

However, analyzing the performance metrics reveals that the current single-list approach is already performing well (combined score 270.50). The key insight is that we need to create a two-tier protection hierarchy without adding the complexity of multiple physical lists, which could introduce overhead.

Instead, I propose:
1. Add a "promotion_tier" flag in metadata for folios that achieve very high access counts (≥ 7 after decay)
2. Give these promoted folios a longer protection window (200ms vs 50ms base)
3. Protect promoted folios even when session is not active, but still apply decay to prevent stale promotions
4. Use the existing access_tier field to track promotion status (tier 3 = promoted)

This approach:
- Maintains the single-list simplicity (avoiding bpf_cache_ext_list_iterate_extended complexity)
- Creates a clear protection hierarchy: cold (tier 0) < warm (tier 1) < hot (tier 2) < promoted (tier 3)
- Protects truly critical pages that repeatedly demonstrate high access frequency
- Still allows eviction of promoted pages if they age out (decay mechanism)
- Should help with the zipfian workloads (ycsb_a, ycsb_b, ycsb_c, ycsb_f) by better protecting the hot set
</DESCRIPTION>
