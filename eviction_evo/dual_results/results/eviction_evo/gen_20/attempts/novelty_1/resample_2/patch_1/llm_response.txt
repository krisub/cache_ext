congestion_adaptive_tier_promotion

<DESCRIPTION>
The current program uses fixed access count thresholds for tier promotion (access_count >= 2 for warm, >= 4 for hot), regardless of network conditions. This is suboptimal because:

1. During high congestion (score > 700), cache misses are extremely expensive (high RTT, retransmissions). The working set should be identified and promoted to hot tier MORE AGGRESSIVELY to minimize these costly misses. Waiting for 4 accesses is too conservative.

2. During low congestion (score < 300), cache misses are cheaper. We can afford to be more selective about hot tier promotion, requiring MORE accesses before promoting to reduce false positives from one-time access spikes.

The current best-performing program (324.29) already implements tier-specific adaptive windowing in the eviction callbacks, which scales protection based on congestion. This proposal extends that pattern to the promotion logic in `evolved_folio_accessed()`.

By dynamically adjusting promotion thresholds based on congestion score:
- High congestion (> 700): Lower thresholds (warm at 1 access, hot at 2) to quickly identify and protect the working set when misses are most expensive
- Medium congestion (300-700): Standard thresholds (warm at 2, hot at 4) 
- Low congestion (< 300): Raise thresholds (warm at 3, hot at 6) to be more selective and maintain aggressive eviction

This directly addresses the dual_small_vs_large trace where the program achieves strong throughput (314.32 in the best case) but could benefit from faster working-set identification during congestion. The dual_congested trace shows even stronger performance (334.92), suggesting the tier system is working well but could be further optimized by making promotion decisions network-aware, not just eviction decisions.

The implementation computes adaptive thresholds at the point of access, using the same congestion_score computation already present in the code, ensuring consistency with the existing adaptive windowing logic.
</DESCRIPTION>
