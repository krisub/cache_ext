<DESCRIPTION>
The current best program (Generation 7, score 324.29) uses tier-specific recency windows that expand with congestion but doesn't adapt them based on burst detection. Looking at the performance metrics, the current program (score 310.27) introduced access count decay which may be interfering with the burst protection mechanism.

The key insight is that during sustained burst phases (multiple consecutive packets within 5ms), the working set is actively being accessed and we should tighten recency windows to evict stale pages more aggressively. This is the opposite of what happens during congestion - bursts indicate high throughput potential, so we should be more aggressive about reclaiming memory from pages that aren't part of the active working set.

Specifically, I propose:
1. Track burst duration (consecutive burst packets) in a global counter
2. When we detect 8+ consecutive burst packets (sustained high-throughput phase), reduce the cold tier recency window by 30% to enable faster eviction of truly cold pages
3. When we detect 6+ consecutive burst packets, reduce the warm tier window by 20%
4. Reset the burst counter when inter-arrival time exceeds the burst threshold

This directly addresses the recommendation by making recency windows adaptive to sustained burst phases, enabling more aggressive eviction during high-throughput periods while maintaining protection during congestion spikes. The dual_small_vs_large trace (currently at 292.13, down from 314.32 in Gen 7) should benefit most since it has a fast reader that creates sustained bursts.

The implementation adds minimal overhead (one global counter increment/reset per packet) and only applies the tightening during confirmed sustained bursts, avoiding premature eviction during transient spikes.
