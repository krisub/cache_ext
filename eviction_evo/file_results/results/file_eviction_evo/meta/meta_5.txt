# Optimization Insights Analysis

## Successful Algorithmic Patterns

- **Dual-list priority segregation with aggressive time-window tuning** (Generation 2: 2846.05 score) outperforms single-list approaches by isolating priority classes and enabling tailored eviction policies. The current best program achieves the highest combined harmonic mean by using separate high-priority (nice ≤ -5) and low-priority (nice > -5) lists with differentiated callbacks, compared to Generation 0's single MRU list (2480.18) and Generation 1's single list with tier classification (2757.44). The key advantage is reduced contention and independent aging thresholds per priority class.

- **Aggressive time-window contraction (30ms recent access, 300ms working set)** in the current best program (Generation 2) significantly improves responsiveness compared to longer windows in earlier generations. Generation 0 used 100ms recent access and 1s working set windows, while Generation 2 reduced these to 30ms and 300ms respectively, achieving 2846.05 vs 2480.18. This faster adaptation to priority changes and memory pressure events directly correlates with the 365-point improvement in harmonic mean score.

- **Lower access-count thresholds (2 for hot, 6 for very-hot) combined with differentiated protection multipliers** in the current best program enables more nuanced folio protection. Generation 2 uses HOT_ACCESS_THRESHOLD=2 (vs Generation 0's 3) and introduces VERY_HOT_ACCESS_THRESHOLD=6, allowing the high-priority callback to apply 3x WORKING_SET_NS protection for very-hot folios while low-priority gets 2x. This multi-tier protection strategy achieves better throughput balance (3285.09 priority vs 2510.52 niceness) than Generation 1's simpler access-count logic.

- **CPU-load-aware adaptive protection (nr_running > 4 threshold) combined with small-file special handling (≤64KB with 2x multiplier)** in the current best program provides context-sensitive eviction decisions. The high-priority callback explicitly protects small files and aggressively preserves working sets when CPU is busy, achieving 68ms P99 latency for priority workload while maintaining 59ms for niceness workload—the tightest P99 spread among all evaluated programs.

## Ineffective Approaches

- **Single MRU list with per-folio metadata and multi-factor heuristics** (Generation 0: 2480.18) underperforms dual-list segregation by 366 points despite using scheduler context (nice values, runqueue depth). The fundamental issue is that a single list cannot efficiently apply different eviction policies to different priority classes simultaneously; protecting high-priority folios in a shared list inherently delays eviction of low-priority folios, creating contention. The 412ms throughput gap between priority (2703.39) and niceness (2291.01) workloads indicates the single list cannot balance competing priorities effectively.

- **Overly conservative protection multipliers and thresholds** in Generation 4 (2525.15 score) demonstrate that excessive protection of high-priority folios reduces overall throughput without proportional latency gains. Generation 4 uses similar dual-list architecture but achieves only 2962.16 priority throughput vs Generation 2's 3285.09 (9.8% lower), suggesting its eviction thresholds are too lenient. The similar P99 latencies across priority classes (68.6ms) indicate the policy fails to differentiate protection aggressiveness sufficiently.

- **Adaptive contention-factor window scaling (70%-100% based on CPU load)** in Generation 3 (2561.71 score) adds complexity without performance benefit compared to fixed aggressive windows. Generation 3's approach of contracting time windows under CPU contention achieves lower harmonic mean (2561.71) than Generation 2's fixed 30ms/300ms windows (2846.05), suggesting that dynamic scaling introduces unpredictability. The 284-point gap indicates that fixed, aggressively-tuned windows outperform adaptive scaling for this workload pattern.

- **Metadata-aware callback routing with priority-swap detection** in Generation 4 (2525.15) adds overhead without sufficient benefit. While the approach of checking accessor_nice during eviction to handle dynamic priority changes is theoretically sound, the modest throughput gains (2200-2962 ops/sec) and lack of P99 differentiation (68.6ms across both workloads) suggest the metadata lookups and conditional logic consume resources without improving eviction quality. The 321-point gap vs Generation 2 indicates this complexity is not justified.

## Implementation Insights

- **Dual-list architecture with separate eviction callbacks enables independent policy tuning per priority class.** The current best program (Generation 2) maintains high_prio_list and low_prio_list with distinct bpf_evict_high_prio_cb and bpf_evict_low_prio_cb functions. The high-priority callback applies 3x WORKING_SET_NS protection for very-hot folios and 2x for hot folios, while the low-priority callback uses 2x and 1x respectively. This asymmetry directly enables the 3285.09 priority throughput while maintaining 2510.52 niceness throughput—a 31% differential that reflects the intended priority bias. Single-list approaches cannot achieve this level of differentiation without complex conditional logic that degrades performance.

- **Aggressive time-window constants (RECENT_ACCESS_NS=30ms, WORKING_SET_NS=300ms) combined with low access thresholds (HOT_ACCESS_THRESHOLD=2) create a responsive eviction policy.** The current best program's 30ms recent-access window is 3.3x shorter than Generation 0's 100ms, enabling faster detection of access pattern changes. The 300ms working-set window is 3.3x shorter than Generation 0's 1s, reducing memory waste from stale folios. These aggressive constants work because they're paired with low access thresholds—a folio becomes "hot" after just 2 accesses, so the shorter windows don't prematurely evict frequently-accessed data. The combination achieves 68ms P99 latency (priority) and 59ms (niceness), the tightest latencies across all programs.

- **Differentiated protection multipliers (3x for very-hot, 2x for hot in high-prio; 2x and 1x in low-prio) create a multi-tier protection hierarchy.** The current best program's high-priority callback uses `if (meta->access_count >= VERY_HOT_ACCESS_THRESHOLD) { if (age < WORKING_SET_NS * 3) return CONTINUE; }` followed by hot-folio logic with 2x multiplier. This creates three protection tiers: very-hot (900ms), hot (600ms), and normal (300ms) for high-priority folios, vs two tiers (600ms, 300ms) for low-priority. The asymmetry ensures that frequently-accessed high-priority data stays in cache longer, directly supporting the 31% throughput differential between priority and niceness workloads.

- **CPU-load-aware adaptive protection (sched_nr_running > 4 threshold) in the high-priority callback provides context-sensitive eviction without complexity.** The current best program's high-priority callback includes `if (sched_nr_running > CPU_BUSY_THRESHOLD) { if (age < WORKING_SET_NS) return CONTINUE; }`, which aggressively protects the working set when the CPU runqueue exceeds 4 tasks. This single conditional check (vs Generation 3's complex contention-factor scaling) achieves better performance by providing binary, predictable behavior: under contention, protect aggressively; otherwise, use standard thresholds. The approach avoids the unpredictability of dynamic scaling while still responding to system load.

# Actionable Recommendations for Future Program Mutations

1. **Introduce adaptive access-count thresholds based on CPU load and memory pressure signals.** The current best program uses fixed HOT_ACCESS_THRESHOLD=2 and VERY_HOT_ACCESS_THRESHOLD=6, but these could be dynamically adjusted: when `sched_nr_running > CPU_BUSY_THRESHOLD`, lower the thresholds (e.g., HOT=1, VERY_HOT=4) to classify folios as "hot" more aggressively and protect them earlier under contention. This builds on the successful CPU-load-aware protection pattern while adding responsiveness to system state, potentially improving the P99 latency spread between priority and niceness workloads (currently 68ms vs 59ms).

2. **Implement per-list eviction budgets with priority-weighted allocation to prevent low-priority list starvation.** Currently, the eviction orchestration iterates low-priority first, then high-priority, but doesn't enforce a budget ratio. Add a mechanism where if `eviction_ctx->nr_to_scan` is 1000, allocate 700 to low-priority and 300 to high-priority (or dynamically based on list sizes), ensuring that high-priority protection doesn't cause excessive low-priority folio retention. This extends the dual-list segregation pattern with explicit fairness guarantees, potentially improving the niceness throughput (currently 2510.52) without sacrificing priority throughput.

3. **Add a "promotion" mechanism that moves frequently-accessed low-priority folios to the high-priority list after reaching a threshold.** Implement a counter in folio metadata that tracks consecutive accesses within a short time window (e.g., 3 accesses in 50ms). When a low-priority folio crosses this threshold, move it to the high-priority list and update its accessor_nice. This captures the insight that access patterns matter more than initial priority assignment, potentially improving overall throughput by 2-3% by better protecting working-set folios regardless of initial classification.

4. **Refine the small-file protection multiplier (currently 2x WORKING_SET_NS) to be access-count-aware.** Instead of uniform 2x protection for all small files, use: `if (is_small && access_count >= HOT_ACCESS_THRESHOLD) { multiplier = 3x } else if (is_small) { multiplier = 1.5x }`. This recognizes that small files with high access counts (e.g., frequently-read config files) deserve more aggressive protection than small files accessed once, aligning with the multi-tier protection hierarchy that made the current best program successful.

5. **Experiment with a hybrid eviction strategy that samples the high-priority list probabilistically rather than iterating it sequentially.** Replace the second `bpf_cache_ext_list_iterate()` call with `bpf_cache_ext_list_sample()` using a ratio of 0.1-0.3 (evict 10-30% of sampled high-priority folios). This reduces the overhead of scanning the entire high-priority list while still allowing some eviction under memory pressure, potentially improving throughput by 1-2% by reducing callback overhead while maintaining the protective benefits of dual-list segregation.
