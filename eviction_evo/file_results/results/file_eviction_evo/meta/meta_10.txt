# Optimization Insights Analysis

## Successful Algorithmic Patterns

- **Dual-list priority segregation with aggressive time-window tuning (30ms/300ms) remains the highest-performing architecture across all evaluated generations.** The current best program (Generation 2: 2846.05 harmonic mean) achieves this through separate high-priority (nice ≤ -5) and low-priority (nice > -5) LRU lists with differentiated eviction callbacks. The consistency of dual-list segregation at the top of the performance hierarchy (Generations 2, 5, 7, 9 all score above 2640) versus single-list approaches (Generation 0: 2480.18, Generation 1: 2757.44) demonstrates that architectural simplicity with aggressive tuning outperforms added complexity.

- **Aggressive time-window constants (RECENT_ACCESS_NS=30ms, WORKING_SET_NS=300ms) combined with low access thresholds (HOT_ACCESS_THRESHOLD=2, VERY_HOT_ACCESS_THRESHOLD=6) create the optimal responsiveness-protection balance.** The current best program achieves 3285.09 priority throughput and 2510.52 niceness throughput with these constants. Generation 5 uses identical time windows and achieves 3087.14 priority throughput (6.0% lower) and 2628.16 niceness throughput (4.7% higher), indicating the constants are sound but Generation 5's callback logic is slightly less effective. Generation 6 uses the same constants but adds contention-aware adaptive scaling (sched_nr_running > 7 threshold), resulting in 2923.57 priority throughput (11.0% lower) and 2151.36 niceness throughput (14.3% lower), demonstrating that fixed aggressive windows outperform adaptive scaling. The 30ms recent-access window is 3.3× shorter than Generation 0's 100ms baseline, enabling faster detection of priority changes, while the 300ms working-set window is 3.3× shorter than Generation 0's 1s baseline, reducing memory waste from stale folios. This aggressive tuning directly correlates with the tightest P99 latencies: Generation 2 achieves 68ms (priority) and 59ms (niceness), compared to Generation 5's 72.2ms and 62.2ms, a 5.9% and 5.1% increase in tail latency respectively.

- **Differentiated protection multipliers (3× for very-hot, 2× for hot in high-priority; 2× and 1× in low-priority) create a multi-tier protection hierarchy that maximizes priority differentiation without sacrificing absolute throughput.** The current best program's high-priority callback applies `WORKING_SET_NS * 3` (900ms) for very-hot folios, `WORKING_SET_NS * 2` (600ms) for hot folios, and `WORKING_SET_NS` (300ms) for recently-accessed folios, while the low-priority callback uses `WORKING_SET_NS * 2` (600ms) for very-hot, `WORKING_SET_NS * 2` (600ms) for hot, and `WORKING_SET_NS` (300ms) for recently-accessed. Generation 5 uses identical multiplier logic and achieves a 17.5% differential (3087.14 / 2628.16 = 1.175×), indicating that callback implementation details matter; Generation 5's slightly different eviction logic (stricter age thresholds and access-count protections) reduces the priority bias. Generation 7 introduces dynamic promotion of hot low-priority folios (8+ accesses) to the high-priority list, achieving a 35.8% differential (3208.35 / 2361.44 = 1.358×) but at the cost of 2.3% lower absolute priority throughput (3208.35 vs 3285.09), demonstrating that promotion logic increases priority bias but reduces overall throughput.

- **CPU-load-aware adaptive protection (sched_nr_running > 4 threshold) in the high-priority callback provides context-sensitive eviction with minimal complexity overhead.** The current best program's high-priority callback includes a single conditional check: `if (sched_nr_running > CPU_BUSY_THRESHOLD) { if (age < WORKING_SET_NS) return CONTINUE_ITER; }`, which aggressively protects the working set when CPU runqueue exceeds 4 tasks. ## Ineffective Approaches

- **Contention-aware adaptive thresholds that dynamically scale protection windows based on CPU load reduce performance compared to fixed aggressive windows.** Generation 6 implements adaptive time-window thresholds that tighten under CPU contention (sched_nr_running > 7), achieving a combined harmonic mean of 2478.71, which is 12.9% lower than Generation 2's 2846.05. The feedback notes that while the approach is theoretically sound for balancing protection under load, the actual performance degradation suggests that dynamic scaling introduces unpredictability: the policy must constantly re-evaluate thresholds as CPU load fluctuates, potentially causing thrashing where folios are evicted and re-added as load crosses the contention threshold. Generation 3 (from previous insights) used similar adaptive contention-factor scaling (70%-100% based on CPU load) and achieved 2561.71, a 10.0% reduction from Generation 2, confirming the pattern. The fixed aggressive windows in Generation 2 (30ms/300ms) provide deterministic behavior that avoids this thrashing, enabling consistent high throughput.

- **Metadata-aware callback routing with priority-swap detection and stale-routing checks adds complexity without sufficient performance benefit.** Generation 6 implements stale-routing detection in eviction callbacks (checking actual priority vs list membership) to handle priority changes, achieving 2478.71 harmonic mean, 12.9% lower than Generation 2. The feedback acknowledges that the approach provides robustness against priority changes but notes that the metadata lookups and conditional logic consume resources without improving eviction quality. Generation 4 (from previous insights) used similar metadata-aware routing with priority-swap detection and achieved 2525.15, a 11.2% reduction from Generation 2. The pattern indicates that the overhead of checking and re-routing misclassified folios outweighs the benefit of handling priority changes dynamically. Generation 2's simpler approach—classifying folios at add/access time and moving them to the appropriate list—avoids this overhead while still handling priority changes through the folio_accessed callback.

- **Hot low-priority folio promotion to high-priority list reduces absolute throughput despite increasing priority-niceness differential.** Generation 7 implements dynamic promotion logic that moves frequently-accessed low-priority folios (8+ accesses) to the high-priority list, achieving 3208.35 priority throughput and 2361.44 niceness throughput (35.8% differential). While the differential is higher than Generation 2's 31%, the absolute priority throughput is 2.3% lower (3208.35 vs 3285.09), and the combined harmonic mean is 4.4% lower (2720.51 vs 2846.05). The feedback notes that the promotion logic "effectively maximizes throughput" but the actual scores contradict this claim. The issue is that promotion moves folios from the low-priority list (where they can be evicted aggressively) to the high-priority list (where they receive strong protection), reducing the effective eviction rate and causing memory pressure to build. This forces more aggressive eviction of other high-priority folios, reducing overall throughput. Generation 2's simpler approach—keeping folios in their original list and applying differentiated protection multipliers—avoids this throughput penalty.

- **Weighted scoring that combines multiple factors (recency, access frequency, small-file protection, CPU contention) introduces complexity that degrades performance compared to threshold-based logic.** Generation 9 implements weighted scoring in the `should_protect_folio()` function that computes dynamic protection windows combining recency, access frequency, small-file protection multipliers (up to 3×), and CPU contention awareness. This achieves 2641.87 harmonic mean, 7.2% lower than Generation 2's 2846.05, with 2911.20 priority throughput (11.4% lower) and 2418.16 niceness throughput (3.7% lower). The feedback notes that the approach "successfully prioritizes responsive I/O" but the actual performance degradation indicates that the weighted scoring introduces overhead and unpredictability. The issue is that weighted scoring requires computing multiple factors for each folio during eviction, consuming CPU cycles that could be spent on actual eviction. Generation 2's simpler threshold-based logic—checking age against fixed constants and access counts—avoids this overhead while achieving better performance.

## Implementation Insights

- **Dual-list architecture with separate eviction callbacks enables independent policy tuning per priority class without conditional branching overhead.** The current best program (Generation 2) maintains `high_prio_list` and `low_prio_list` with distinct `bpf_evict_high_prio_cb` and `bpf_evict_low_prio_cb` functions. The high-priority callback applies 3× WORKING_SET_NS protection for very-hot folios and 2× for hot folios, while the low-priority callback uses 2× and 1× respectively. This architectural separation means that during eviction, the kernel calls the appropriate callback for each list without needing to check the folio's priority inside the callback—the callback itself is the policy. Comparing to Generation 9's weighted scoring approach, which uses a single `should_protect_folio()` function that must compute multiple factors and check CPU contention for every folio, the dual-callback approach avoids repeated conditional checks. The performance difference (2846.05 vs 2641.87) reflects this efficiency gain: Generation 2's callbacks are simpler and faster, enabling more folios to be evaluated during each eviction cycle. Generation 5 uses identical dual-callback architecture and achieves 2839.22 (99.8% of Generation 2), confirming that the architectural pattern is sound.

- **Aggressive time-window constants paired with low access thresholds create a responsive eviction policy that adapts quickly to priority changes without thrashing.** The current best program uses RECENT_ACCESS_NS=30ms, WORKING_SET_NS=300ms, HOT_ACCESS_THRESHOLD=2, and VERY_HOT_ACCESS_THRESHOLD=6. The 30ms recent-access window is short enough to detect priority changes within a single I/O burst (typical I/O latency is 1-10ms), while the 300ms working-set window is long enough to retain frequently-accessed data across multiple I/O operations. The low access thresholds (2 for hot, 6 for very-hot) mean that a folio becomes "hot" after just 2 accesses, so the short windows don't prematurely evict frequently-accessed data. This combination creates a responsive policy: when a high-priority process accesses a folio, it's immediately classified as hot and protected for 600ms (2× WORKING_SET_NS); when a low-priority process accesses the same folio, it's protected for only 600ms in the low-priority list (2× WORKING_SET_NS for hot), creating a clear priority bias.
