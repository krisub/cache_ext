- **Dual-list priority segregation with aggressive time-window tuning (30ms/300ms) and demotion mechanisms achieves the highest performance when combined with asymmetric protection multipliers.** The current best program (Generation 13: 2911.51 harmonic mean) implements dual-list architecture with a novel demotion mechanism that moves single-access aged folios from high-priority to low-priority lists, preventing one-time accesses from consuming high-priority slots. Generation 14 (2896.69 harmonic mean, 3402.81 priority throughput, 2521.63 niceness throughput) also implements demotion but achieves 0.5% lower harmonic mean than Generation 13, suggesting that Generation 13's specific demotion threshold (single-access folios aged beyond 2× WORKING_SET_NS) is more effective than Generation 14's approach. The demotion mechanism directly addresses the inefficiency identified in previous insights: instead of allowing one-time accesses to occupy high-priority slots indefinitely, the policy actively demotes cold high-priority folios, freeing slots for frequently-accessed data while maintaining protection for genuinely hot pages.

- **Asymmetric protection multipliers (3× for very-hot, 2× for hot in high-priority; 2× and 1× in low-priority) combined with aggressive time windows (30ms/300ms) create optimal priority differentiation without sacrificing absolute throughput.** The current best program applies these multipliers consistently: very-hot high-priority folios receive 900ms protection (3× WORKING_SET_NS), hot high-priority folios receive 600ms (2× WORKING_SET_NS), while very-hot low-priority folios receive 600ms (2× WORKING_SET_NS) and hot low-priority folios receive 600ms (2× WORKING_SET_NS). This asymmetry achieves a 40.2% priority-niceness throughput differential (3496.15 / 2494.39 = 1.402×), which is 9.2% higher than Generation 2's 31% differential (1.31×) and 19.5% higher than Generation 11's 24.3% differential (1.243×). The key insight is that Generation 13's high-priority callback applies stricter protection thresholds (very-hot requires age < 900ms, hot requires age < 600ms) while the low-priority callback applies more lenient thresholds (very-hot requires age < 300ms, hot requires age < 600ms), creating a clear priority bias. This contrasts with Generation 11, which uses identical protection logic for both lists (very-hot requires age < 300ms in both), resulting in lower priority differentiation. The 40.2% differential in Generation 13 demonstrates that asymmetric multipliers are more effective than symmetric protection when combined with demotion mechanisms.

- **CPU-load-aware adaptive protection using a simple binary threshold (sched_nr_running > 4) provides context-sensitive eviction that maintains high throughput under load.** The current best program's high-priority callback includes a conditional check: `if (sched_nr_running > CPU_BUSY_THRESHOLD) { if (age < WORKING_SET_NS) return CONTINUE_ITER; }`, which aggressively protects the working set when CPU runqueue exceeds 4 tasks. Comparing to Generation 11 (which uses identical CPU-busy logic), Generation 13 achieves 1.5% lower priority P99 latency (66.9ms vs 67.9ms) and 23.6% higher priority throughput (3496.15 vs 3107.92), indicating that the demotion mechanism improves both latency and throughput. The binary threshold approach avoids the complexity of adaptive scaling (as seen in Generation 6, which achieved 12.9% lower performance), instead providing predictable behavior that enables consistent high throughput. The CPU-busy threshold of 4 tasks is conservative enough to protect working sets during moderate load while remaining responsive during idle periods, balancing protection with eviction aggressiveness.

- **Demotion mechanism that moves single-access aged folios (age > 2× WORKING_SET_NS) from high-priority to low-priority lists prevents memory waste while maintaining protection for frequently-accessed data.** The current best program implements this in the high-priority callback: `if (meta->access_count == 1 && age > WORKING_SET_NS * 2) { bpf_cache_ext_list_del(node->folio); bpf_cache_ext_list_add_tail(low_prio_list, node->folio); }`. ## Ineffective Approaches

- **Overly conservative protection thresholds for high-priority folios (extending protection to 3× WORKING_SET_NS for very-hot pages) can cause memory pressure to build, degrading overall throughput despite improving priority differentiation.** Generation 14 implements very conservative protection: very-hot high-priority folios receive 900ms protection (3× WORKING_SET_NS), identical to Generation 13. However, Generation 14 achieves 2896.69 harmonic mean compared to Generation 13's 2911.51 (0.5% lower), with 3402.81 priority throughput (2.7% lower) and 2521.63 niceness throughput (1.1% higher). The feedback for Generation 14 notes that "the very conservative protection thresholds for high-priority folios (up to 3× working set window) may cause memory pressure to build before sufficient pages are freed," suggesting that the conservative approach delays eviction and causes memory pressure spikes. Generation 13 achieves higher throughput despite using identical protection multipliers, indicating that the demotion mechanism in Generation 13 is more effective at preventing memory pressure buildup. The pattern suggests that while aggressive protection multipliers are beneficial, they must be paired with active demotion mechanisms to prevent cold pages from occupying high-priority slots indefinitely. Without demotion, the conservative thresholds cause memory pressure to accumulate, forcing more aggressive eviction of other pages and reducing overall throughput.

- **Adaptive threshold reduction under CPU contention (hot_threshold: 2→1, very_hot_threshold: 6→4 when sched_nr_running > 4) introduces unpredictability that degrades performance compared to fixed aggressive thresholds.** Generation 11 implements adaptive threshold reduction: when CPU is busy (sched_nr_running > 4), the hot threshold reduces from 2 to 1 and the very-hot threshold reduces from 6 to 4, making it easier for folios to be classified as hot/very-hot and receive protection. This achieves 2771.08 harmonic mean, 5.1% lower than Generation 13's 2911.51. The feedback for Generation 11 notes that "the adaptive threshold reduction under CPU contention effectively balances working-set retention with eviction pressure during high load," but the actual performance data contradicts this claim. The issue is that dynamic threshold adjustment introduces unpredictability: as CPU load fluctuates around the contention threshold, the classification of folios changes, potentially causing thrashing where folios are reclassified and re-protected as load crosses the threshold. Generation 13 uses fixed thresholds (HOT_ACCESS_THRESHOLD=2, VERY_HOT_ACCESS_THRESHOLD=6) regardless of CPU load, achieving 5.1% higher performance, confirming that fixed aggressive thresholds outperform adaptive scaling. The pattern aligns with previous insights showing that adaptive scaling (Generation 6: 12.9% lower performance) consistently underperforms fixed aggressive tuning.

- **Identical protection logic for both high-priority and low-priority lists reduces priority differentiation and throughput compared to asymmetric protection multipliers.** Generation 11 applies identical protection thresholds to both lists: very-hot folios (6+ accesses) receive age < 300ms protection in both lists, hot folios (2+ accesses) receive age < 300ms protection in both lists. This achieves 2771.08 harmonic mean and 24.3% priority-niceness differential (3107.92 / 2500.11 = 1.243×). Generation 13 uses asymmetric multipliers: very-hot high-priority folios receive 900ms protection while very-hot low-priority folios receive 300ms protection, achieving 2911.51 harmonic mean and 40.2% differential (3496.15 / 2494.39 = 1.402×). The issue with symmetric protection is that it fails to create sufficient priority bias: both high-priority and low-priority folios receive identical protection, so the policy cannot effectively prioritize high-priority workloads. Asymmetric multipliers directly address this by applying stronger protection to high-priority folios, enabling the policy to maintain high throughput for priority workloads while allowing faster eviction of low-priority pages.

This prevents the callback from wasting CPU cycles evaluating protection logic for folios that will be demoted anyway. Generation 14 uses similar demotion logic but achieves 0.5% lower harmonic mean, suggesting that Generation 13's specific placement and threshold are more optimal. The key insight is that demotion should be integrated into the eviction callback rather than implemented as a separate mechanism, minimizing overhead while maximizing effectiveness.

The pattern shows that the most effective implementations use fixed constants and simple conditional logic rather than dynamic computation.

- **Binary CPU-load-aware protection (sched_nr_running > 4 threshold) provides context-sensitive eviction through a single conditional check, avoiding the overhead of adaptive scaling or contention-factor computation.** The current best program's high-priority callback includes: `if (sched_nr_running > CPU_BUSY_THRESHOLD) { if (age < WORKING_SET_NS) return CONTINUE_ITER; }`, which aggressively protects the working set when CPU runqueue exceeds 4 tasks.
