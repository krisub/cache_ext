two_tier_survivor_promotion
</NAME>

<DESCRIPTION>
The current program uses a single main_list with scoring-based eviction. The recommendation suggests implementing a two-tier list structure to reduce thrashing during sustained congestion.

The key insight is that folios which survive multiple consecutive eviction scans are likely part of the core working set and should be protected more aggressively. By tracking a `survival_count` and promoting folios that survive 3+ scans to a "survivor_list", we can:

1. Reduce cache thrashing by protecting proven working-set items
2. Apply a 0.5x score multiplier to survivor-tier folios (half as evictable)
3. Maintain better performance during network congestion where each cache miss is expensive

This builds naturally on the current scoring mechanism: survivor folios get permanently reduced eviction scores, making them "sticky" in cache without needing complex list manipulation at every access.

The implementation adds:
- A `survival_count` field to track how many eviction scans each folio has survived
- A separate `survivor_list` for promoted folios
- Logic to promote folios after 3 survival scans
- A 0.5x multiplier to survivor scores (0.75 in fixed-point arithmetic to avoid division)
- Proper cleanup in folio_evicted to handle both lists
</DESCRIPTION>

// -- struct_ops: folio_evicted ------------------------------------------------
void BPF_STRUCT_OPS(evolved_folio_evicted, struct folio *folio)
{
    if (!is_folio_relevant(folio))
        return;

    u64 key = (u64)folio;
    struct net_folio_metadata *meta =
        bpf_map_lookup_elem(&folio_metadata_map, &key);

    // Remove from both lists if tracked
    if (meta) {
        // Remove from main_list
        bpf_cache_ext_list_del(folio);
        
        // Remove from survivor_list if promoted
        if (meta->is_survivor) {
            bpf_cache_ext_list_del(folio);
        }
    } else {
        // Fallback: try to remove from main list anyway
        bpf_cache_ext_list_del(folio);
    }

    bpf_map_delete_elem(&folio_metadata_map, &key);
    bump_counter(5);
}
